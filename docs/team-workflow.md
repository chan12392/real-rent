담당자는 폴더의 주 작업자다. 다른 영역을 바꾸어야 하면 담당자와 먼저 합의한다.
특히 `app/main.py`, `app/schemas/`, `backend/pyproject.toml`, `backend/uv.lock`,
`docs/api.md` 변경은 개발 2가 조율한다. 잠금 파일은 수동으로 합치지 않고 `uv`로 갱신한다.
자동 검사는 각 구현자가 작성하고 분석 담당자가 결과를 취합한다.

## 한 작업의 순서

1. 이슈에 목적, 담당 경로, 완료 기준을 적고 담당자를 정한다.
2. 최신 `origin/main`에서 본인 작업 브랜치를 만든다.
3. API·데이터 구조를 바꿀 경우 예시부터 공유한다. 상대 기능이 없어도 샘플로 병렬 개발한다.
4. 담당 기능을 구현하고 해당 검사와 실제 연결 경로를 확인한다.
5. 작은 PR을 열고 변경 내용·검증·미확인 사항을 적는다.
6. 다른 팀원의 리뷰가 끝나면 `chan12392`가 병합한다.

이슈·PR의 작성자와 리뷰어는 GitHub에서 실제 팀원 계정으로 지정한다.
역할과 계정의 대응은 팀에서 정한다. 문서에 임의의 계정이나 자동 리뷰어를 고정하지 않는다.

## 브랜치 사용

역할별 첫 브랜치 이름의 예시는 `feat/dev1-ui`, `feat/dev2-backend`,
`feat/dev3-ai`, `feat/analysis-domain`이다. 담당자마다 작은 기능 PR로 나눈다.
공통 구조 PR은 먼저 다른 팀원의 리뷰를 받고 `chan12392`가 병합한다.

공통 구조를 포함해 미리 만든 후속 브랜치는 공통 PR에 의존한다.
공통 PR 병합 전에도 후속 브랜치에서 구현할 수 있다. 기능 PR은 공통 PR이 병합된 뒤
최신 `origin/main`을 반영하고 `main`을 대상으로 연다. 공통 PR이 수정되면 후속 브랜치도 갱신한다.
서로 다른 기능을 한 역할 브랜치에 계속 쌓지 않는다.
